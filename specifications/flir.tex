\section{Introduction}

This document is intended as a reference specification for FLIR (First-order Logic Intermediate Representation). FLIR is the language emitted by the Coln compiler.

This document covers the grammar of FLIR and its intended semantics. It does not cover the production of FLIR from the Coln language, or the precise details of the implementation for these semantics.

\section{Tables}

There are three types of tables in FLIR: ground tables, cons tables, and view tables.

\begin{definition}
  A \defcase{ground table} contains the actual data of the database. That is, a commit logically speaking is only about the changes to the ground tables (though, for efficiency reasons we may cache changes to other tables).

  Ground tables may have \emph{primary keys}: see Definition~\ref{def:primary-key}.
\end{definition}

\begin{definition}
  A \defcase{cons table}, logically speaking, ``contains everything that it is allowed to contain.'' That is, if an entry in a cons table is allowed by the \emph{laws} (\S\ref{sec:laws}), then it should be considered to logically exist. However, it should only be in the table \emph{once}; this may be implemented by deduplication (that is, a \emph{hash}cons), or alternatively just by implementing equality with structural comparison rather than id comparison.

  In practice, users make explicit inserts into cons tables; these inserts should be seen as ``scratchwork'' that is only relevant to commits when inserts into ground tables reference the ids produced by the inserts into cons tables.
\end{definition}

\begin{definition}
  A \defcase{view table}, logically speaking, ``contains everything that it is supposed to contain.'' The \emph{rules} (\S\ref{sec:rules}) of the schema explain how to push data from the ground tables into the view tables.
\end{definition}

Conceptually speaking, cons and view tables are quite similar. However, from a database perspective, their validity is maintained in different ways. View tables are valid ``by construction'' in a sense; they only have in them what the rules say should be in them. The user never inserts into a view table, so the database engine doesn't have to check that an arbitrary insert is valid. On the other hand, the cons tables are inserted into manually, so the database engine must check that an arbitrary insert is valid (law enforcement), but the database engine need not eagerly create its own inserts into cons tables.

Tables have row ids which allow unambiguous access to individual rows of the table. Row ids for views are only used internally, but row ids for ground and cons tables can be referenced in other tables. Each row id is unique across the database; two tables may not share row ids.

Each table has a list of columns. A column may either be of primitive type (\syntax{`int'} or \syntax{`string'}), or it may be of row id or union type, referred to by \syntax{<name>}.

\begin{definition} \label{def:primary-key}
  A ground table may have a \defcase{primary key}. The primary key is specified by an integer that identifies a prefix of the columns, the values of which must uniquely identify rows.
\end{definition}

('vertex.foreignKey

\begin{example}
  In Figure~\ref{fig:simple-digraph}, the \verb|(primarykey 2)| primary key constraint says that for any two vertices there may be at most one edge between them.
\end{example}

Mathmatically speaking, a table may be seen as a function from its set of row ids to tuples with entry types given by the column types.

\section{Unions} \label{sec:unions}

\begin{definition}
  A \defcase{union} declares a new column type, the allowable values of which are the union of the row ids for tables listed in the \emph{variants} of the union.
\end{definition}

Given an element of union type, its corresponding table is unambiguous because each row id belongs to at most one table. However, it may be desirable to make the process of looking up the corresponding table more efficient; this may be achieved in a variety of ways.

\section{Propositions} \label{sec:propositions}

\begin{definition} \label{def:term}
  A \defcase{term} is either a literal string, literal integer, a literal row id (hash and counter), or a variable, identified by its position in the context (\verb|%0| is the first variable in the context, \verb|%1| the second variable, etc.). Literal row ids may only appear in terms used in queries (\S\ref{sec:query}) and mutations (\S\ref{sec:mutation}).
\end{definition}

\begin{definition} \label{def:atomic-proposition}
  An \defcase{atomic proposition} consists of a table name along with an optional row id specification (\syntax{<idarg>}) and a sequence of terms. The terms are written in order of the columns of the table, so the number of terms may not exceed the number of columns. The semantics of an atomic proposition is that a row exists in the named table with given id (if provided), and given column values.
\end{definition}

\begin{definition} \label{def:equality-proposition}
  An \defcase{equality proposition} consists of a column type along with two terms of that type. The semantics of an equality proposition are that the two provided terms are equal.
\end{definition}

A proposition is either an atomic or equality proposition.

In general, we often use a sequence of propositions (\syntax{props}): this should be interpreted as the \emph{conjunction} (\(\wedge\)) of all propositions in the sequence.

\section{Laws} \label{sec:laws}

\begin{definition}
  A \defcase{law} consists of
  \begin{itemize}
    \item A status, which may either be \verb|enforced| or \verb|monitored|.
    \item A sequence of types for bound variables (which are identified by index into this sequence, see Definition~\ref{def:term}).
    \item An \defcase{antecedent}, which is a conjunction of propositions.
    \item A \defcase{consequent}, which is a conjunction of propositions.
  \end{itemize}
\end{definition}

The semantics of a law is that for every assignment of variables such that the antecedent holds, the consequent should also hold. In other words, a law is a statement of the form
%
\[ \forall \vec{x}. P(\vec{x}) \Rightarrow Q(\vec{x})\]
%
where \(P\) is the antecedent and \(Q\) is the consequent.

An enforced law (law with status \verb|enforced|) must hold at all times, including in the presence of merge conflicts. A database in violation of enforced laws is an error.

A monitored law (law with status \verb|monitored|) may sometimes not hold; a database in violation of monitored laws may be seen as a ``work in progress'' towards a valid database.

\section{Rules} \label{sec:rules}

\begin{definition}
  A \defcase{rule} consists of
  \begin{itemize}
    \item A sequence of types for bound variables (which are identified by index into this sequence, see Definition~\ref{def:term}).
    \item An \defcase{antecedent}, which is a conjunction of propositions.
    \item A \defcase{consequent}, which is a single atomic proposition whose head is a view table.
  \end{itemize}
\end{definition}

A rule acts as a ``pump'' for filling up its view table. While rules seem similar to laws, the difference is that it is a category error to speak of ``violating'' a rule; there is nothing that a user can do to violate a rule. A rule is merely a directive to the query system that says how to insert rows into view tables. Moreover, rules are the \emph{only} way to produce rows in view tables; the user may not insert into view tables directly.

\section{Queries} \label{sec:query}

\begin{definition}
  A \defcase{query} consists of a context of bound variables, along with a conjunction of propositions in that context.
\end{definition}

\begin{example}
  The following query finds all triangles in a graph.
  \begin{verbatim}
  (query
   ('V 'V 'V 'E 'E 'E)
   (('V (id %0))
    ('V (id %1))
    ('V (id %2))
    ('E (id %3) %0 %1)
    ('E (id %4) %1 %2)
    ('E (id %5) %0 %2)))
  \end{verbatim}
\end{example}
%
\noindent The terms in a query may contain row id literals, in the case that the query is produced dynamically by a program.

The results of a query is the set of all assignments of the bound variables which satisfy the propositions in the body.

\section{Mutations} \label{sec:mutation}

\begin{definition}
  A \defcase{mutation} consists of a sequence of atoms, \emph{without} id parameters.
\end{definition}

\begin{example}
  The following mutation inserts a triangle into a graph
  \begin{verbatim}
  (mutation
    ('V)
    ('V)
    ('V)
    ('E %0 %1)
    ('E %1 %2)
    ('E %0 %2))
  \end{verbatim}
\end{example}
%
\noindent A mutation is interpreted by inserting a new row in the relevant table for each atom. The row ids from previous insertions are available as variables in later insertions, so \verb|('E '%0 %1)| means insert an edge between the vertex inserted in the first instruction and the vertex inserted in the second instruction.
